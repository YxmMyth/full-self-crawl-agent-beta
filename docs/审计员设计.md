# 审计员设计

> 审计在 recon / harvest 的 `mark_done` 时跑，判任务做完没。
> 全程用 kungal（采游戏真实剧本）举例。

## 一句话

**审计员就是一个只读的 agent。** 它拿着一张钉死的语义 checklist，用工具翻真实文件、逐条对照内容找证据、把支撑判定的原文抄出来，查完自然停下、最后一句话就是判决。**复用现有 agent session 那套，不需要任何 Python 编排。**

## checklist（它对照的标准）

从意图的证据标准派生出**可逐条检验的语义标准**——每条都是「能在内容里证伪」的具体 tell，不是「是不是真货」这种开放问题。

kungal 例：
- **C1**：catalog 里每个游戏，data/ 下都有对应文件
- **C2**：文件是**真实对白**——有 `角色名：台词` 的交替结构、是第二人称对白，**不是第三人称剧情概述**
- **C3**：文件非空、非坏、类型正确

要点：
- **WANT 在 intake 钉死；C2 这种「锐利的 tell」要等 recon 看过站点才写得出**，所以在 **gate 阶段定锐利版**再钉死。
- checklist 一旦定，**整个 mission（含 FAIL→重试）钉死稳定**，不让 deepseek 每次审计重新生成、把硬标准洗软。

## 审计员怎么干

它是一个**单独的 agent session**：

- **只读工具**：读文件 / grep / 列压缩包 / ls，沙箱在 `run_dir/{samples,catalog,data,workspace}`。
- **全新上下文**：**看不到 worker 的对话和自我辩解**（独立性靠这个）。
- **briefing**：钉死的 checklist + 证据标准 + 对抗指令——「把完成当未经证明；每条标准都去真实内容里找证据，**把支撑判定的原文几行抄出来**；只引文件大小 / 类型这种结构事实、不算证明语义标准。」
- 它翻真实产物，**逐条判 checklist**，每条：达成 / 没达成 / 拿不准 + **抄出的原文证据**。
- 理解类标准（recon 的 L1-L3）同样打法：World Model 声称「有端点 X / 数据分多页」→ 去 catalog / network 痕迹里找证据，引出来；找不到 = 没达成。
- 查完它**自然停下**（不再调工具），最后那条消息 = 判决。撞 session 步数上限还没结论 → 默认拿不准。

**没有 Python 判官、没有固定流程、没有协议。就是个 agent 在干验收的活。** 数覆盖、对 catalog 这种机械活，它自己用工具数。

## 三种判决

- **PASS** → 完成。
- **FAIL** → 把差的具体条目（+原文证据）回给 worker，让它补。
- **UNCERTAIN** → 上报人确定。死胡同默认落这、**绝不默认 PASS**。

## 为什么这样在 deepseek 上成 + 天花板

- **没有「必须调的提交工具」** → 没有 deepseek 那个「光调查、永不提交」的死锁（判决是它自然停下后的最后一句话，跟 worker 干完活停下来一样）。
- 反 satisficing 的硬度来自三样、**都不是 Python**：**锐利的可逐条检验 checklist + 独立 fresh 的审计 agent + 逼它每条引原文**。把「模型整体好恶投票」变成「逐条对着原文回答 yes/no」——deepseek 更难糊弄。
- **诚实的天花板**：审计员还是 deepseek，不可能 100%。独立性靠 fresh 上下文 + 对抗立场 + 引原文，不靠换模型。
- **审计员锚定「初始意图」**：它的尺子是 intake 钉死的意图内核（WANT + 证据标准），不是派生 checklist、更不看 worker 的框架。把这把尺子写进 briefing、逼它「先读后判、逐条对着意图」，就是反 satisficing 的全部手段。
- **不加机械复核 / 第二只眼（2026-06-09 定）**：架构审查提过两个加固——Python 验「判决前真读过字节」、PASS 后再跑一个独立审计员复核——**都不上**。「审计员可能没真读 / 自信地误判」当**提示词质量问题**调好，不堆机械层、不加冗余 agent。接受天花板。

## 接到哪

recon 的 `mark_done`（`src/verification/audit.py`）和 harvest 的 `mark_done`（`src/harvest/audit.py`）各 spawn 一个只读审计 agent；`AuditResult.overall` 扩成 `{PASS, FAIL, UNCERTAIN}`；各加 UNCERTAIN 分支（不自动 DONE，上报）。

## UNCERTAIN 怎么落地（已定）

审计员判 UNCERTAIN → 走 `ask_human` 文字通道上报人（「这几个样本我拿不准是不是真剧本，你看看 → 」），**卡住等人，不自动续**。无人值守也照样 hold——拿不准的产物绝不偷偷算过（「绝不默认 PASS」的延伸），和 gate 存疑 hold 同形。通道见 `docs/人机交互通道设计.md`。

## 还开着的

- checklist 锐利 tell 的质量，取决于 gate 阶段证据标准写得够不够准。

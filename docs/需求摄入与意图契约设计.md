# 需求 → 意图 → 核验：一根意图贯穿全程

> 给 lead 的设计文档（逐条共识用）
> 日期：2026-06-08
> 配套：`CLAUDE.md` §六（硬约束）、`docs/Planner设计.md`（L1-L4）、`docs/工具重新设计共识.md`

## 1. 现在到底有几个「东西」（先看这个）

怕概念多到对不上，先把账算清楚：**人这边只定义 1 个东西，recon 那边发现 1 个东西，其余全是从这俩派生的视角，不是新对象。**

| 宏观对象 | 谁产生 | 是什么 | 能不能改 |
|---|---|---|---|
| **意图**（唯一被定义 + 保护的核心） | 人 | WANT + 证据标准 + 边界 | 只有人在 2 个 checkpoint 能改；**agent 永远不能改** |
| **universe / catalog**（唯一被发现的） | recon | 站点全集（「该采多少」的真相） | recon 探索时数出来 |

你可能担心的那些，**都不是独立对象**：

- **requirement（原始需求）** = 意图的原始形态（你打的字），编译澄清后成结构化意图。同一个东西。
- **核验标准** = 意图里「证据标准」那一块，收尾时当尺子用。不是单独的东西。
- **recon 目标 / harvest 目标** = 同一个意图在两个阶段「怎么算做完」的两种问法。不是两个对象。
- **recon 完目标会变** = gate 时人校准出意图的新版本。还是那 1 个对象，有版本而已。
- **harvest 的 checklist** = 从意图派生、可重写的草稿建议，不钉死、不算「定义」。

设计的全部用意：**让被定义/保护的东西尽量少（就 1 个意图）**，避免对象增殖导致互相对不上。

## 2. 为什么这么设计：kungal 的教训

需求是「采游戏**剧本**（玩家读到的真实对白）」。系统交了一堆**剧情梗概**（一句话总结），整轮白费。两个根因：

1. **没人在开跑前钉死「剧本 = 真对白，不是梗概」** → 系统自己脑补了个更省事的目标。
2. **审计员是内容瞎子** → 只看文件名 + 大小，读不到字节，分不清真对白和梗概，放行了。

整套设计就是堵这两个洞：**把「什么算真东西」作为意图的核心钉住（防 agent 缩水）+ 让审计员真读内容**。

## 3. 意图：稳定内核 + 流变理解

意图不是一块铁板，它有两层：

| 层 | 是什么 | 稳定性 | 谁能改 |
|---|---|---|---|
| **稳定内核** | 用户的 WANT + **证据标准**（「真东西 vs 廉价替代」） | 稳定。recon 前不懂站点，但「用户要什么」开跑就定了 | **agent 永远不能改**；只有人在 checkpoint 能校准 |
| **流变理解** | 操作性理解 / 可行性 / 各阶段终态 / universe / 计划 | 流变，边跑边学 | agent 自由更新（这是它的工作） |

- **该被钉住的只有内核**，且钉死防的是 **「agent 自己偷偷把目标缩水」（satisficing）**，**不是防「人带新理解来校准」**。
- 所以这不是「不可变契约」，是 **「由人版本化的、活的理解」**。流变合法——只要是**人-gated 的校准**，不是 agent 的漂移。

### 内核长什么样（自由散文，不是表格 schema）

run 根目录一个小文件，纯散文三块：

- **终态**：跑完世界该长啥样。
- **证据标准**：一份真东西具体长啥样 + **哪些便宜替代品必须拒**。← kungal 那块钉子。
- **边界与约束**：范围、硬规矩。**只定性，不写数量**（数量由 recon 发现 → universe-handoff）。

> **§六 守住**：这是**任务级散文**，描述「这次要干成啥」，不是数据字段 / `target_fields`。

kungal 例子里证据标准该写：「样本 = 玩家真正读到的对白行，二进制/编码存的要解码；剧情梗概、标题列表、API 元数据、URL、计数——都不算，审计判 FAIL，且必须打开文件确认。」

## 4. 意图的一生

```
用户 requirement（通常一开始就是最终形态）
   │
   ▼  ① intake（轻：人在就确认一下，把假设摊明）→ 编译成意图内核，钉住
   │      （编译用一次 LLM；若产出垃圾且无人 → 硬停大声报错，绝不揣空意图硬跑）
   ▼
recon 跑（终态 = L1-L4 理解 + 证明样本）  ← 跑中随时能回头看意图
   │
   ▼  ② gate（重：人带 recon 的新信息来校准）→ 必要时改出意图新版本
   │
   ▼
harvest 跑（终态 = 对 universe 全覆盖）
   │
   ▼  核验：审计员从磁盘重读意图当尺子 + 读真实文件内容；没过 → 回流
```

意图被三处引用，但**始终只有一个**：

1. **出生（intake）**：把需求编译成内核 + 摊开假设。
2. **跑中查回**：内核塞进 agent 永不被清除的消息前缀，跑多久都不丢；遇模糊回头看的是原始意图，不是漂移过的脑内转述。
3. **收尾当尺子**：mark_done 时审计员从磁盘**新鲜重读**内核（不信上下文转述），先验它没被 agent 改过，再当合同逐面量。

> **关键接线（红队揪出的）**：recon 完成走 `src/verification/audit.py`，harvest 走 `src/harvest/audit.py`，**是两套独立审计**。意图必须**两套都喂**，否则梗概样本在 recon 就埋下、传染给 harvest，晚一整阶段才发威。

## 5. 两个阶段，两种「算做完」

同一个意图，两阶段要的不一样：

| 阶段 | 终态 | 核验问什么 |
|---|---|---|
| **recon** | 理解 + 证明样本 = **L1-L4**（L1 站点结构 / L2 数据分布 / L3 需求映射 / L4 样本采集） | 真看懂了吗？证明样本是**对的种类**吗（梗概问题在这就得用「读内容」堵，不能等 harvest）？universe 枚举了吗？ |
| **harvest** | 对发现的 universe **全覆盖** | 覆盖全了吗？每条是**真东西**（内容诚实）吗？ |

（L1-L4 是现有骨架；是否有更细更准的版本见 §8。）

## 6. 人机交互：三类，别揉成一类

「问人」有三种，性质不同：

**（A）校准需求/意图 —— 结构性，就 2 个点。**
- **intake（开跑前，轻）** + **gate（recon 完，重）**。这俩是**排好的、几乎必设的 checkpoint**，不是 agent 临时决定要不要。
- gate 才是**主**校准：recon 前几乎全是假设（对站点一无所知），逼着澄清 = 对着未知瞎问；**recon 完信息最全**（universe 出来了、站上有没有真货清楚了），才是和人对齐的最佳时机。
- 「几乎必须」= **槽位结构上永远在**（到这一定停一下、向人 surface），但**问多少随要校准的多少伸缩**：需求一开始就清楚，intake 近乎零；recon 完有新情况，gate 就重。
- **需求/意图只在这 2 个点合法地改**（人版本化，不准 agent 漂移）。

**（B）求操作性帮助 —— agent 当场判断，随时，不碰需求。**
- 登录墙 / 验证码 / 硬茬 / 「我卡住了」——**agent 看实际情况判要不要调**（就是现有 `request_human_assist`）。**只求帮忙，不重新谈需求。**

**（C）卡死/判不准上报 —— agent 或审计员触发，罕见，回流到人。**
- harvest 中段才撞出「根本性错配」（站上压根没有 / 交付物类型判错），gate 已过、后无 checkpoint → agent **不能自己改需求**，而是 **blocked-stop 上报 → 回到人校准**。
- 审计员**判不准（UNCERTAIN）**时同理上报，让人确定，而不是瞎猜 PASS/FAIL。
- 发起靠 agent/审计员判断，改需求权在人。

> **「何时问人」不写成流程图。** 框架只给**通道**（`ask_human`）+ 一条**原则**（「撞真·人类门 / 自己看不出又关键的岔路 → 问」），**扣不扣扳机是 agent 当场判断**（守 §六）。（B）（C）都是 agent 判断；只有（A）是结构性的。

**推论**：2 个校准点确定清楚了，中间就**没必要再对齐需求**。

> **通道形态见 `docs/人机交互通道设计.md`**：两个工具（`request_human_assist` 去操作回 ack / `ask_human` 用话回答回文字）一条通道；三入口（agent 工具 / intake 编译器 / gate）共用；交互界面就在每个 run 的 dashboard 页（已嵌 noVNC）。**intake 澄清改为判断驱动、不卡轮数**（轮次多是「确定性不够」的症状；闸门是「现在还含不含糊」，人不答则 fail closed）。

## 7. 核验怎么做

**审计员就是一个只读的 agent。** 它拿着一张钉死的**语义 checklist**（从意图证据标准派生的、可逐条对照内容检验的标准），用只读工具翻真实文件、逐条找证据、**把支撑判定的原文抄出来**，查完自然停下、最后一句话就是判决。

- 反 satisficing 的硬度来自三样、**都不是 Python**：**独立 fresh 上下文**（看不到 worker 的自我辩解）+ **对抗立场**（把完成当未证明）+ **逼它每条引原文**。把「整体好恶投票」变成「逐条对着原文回答 yes/no」。
- 没有「必须调的提交工具」→ 没有 deepseek 的 tool-use 死锁（判决是它停下后的最后一句话，跟 worker 干完停下来一样）。
- checklist 在 **gate 定锐利版**（C2「真对白非梗概」要 recon 知识）、钉死、跨 retry 稳定。
- 理解类标准（recon L1-L3）同样打法：World Model 的声明 → 去 catalog/network 痕迹里找证据、引出来。

三种结论：PASS / FAIL（回 worker 补）/ UNCERTAIN（死胡同默认落这，上报人，走 §6 的 C）。

> 完整设计见 **`docs/审计员设计.md`**。

## 8. 决定状态

**已定**：
- **gate 无人值守**：recon 审计（含读内容抽查）**干净通过就自动进** harvest，**有任何存疑就 hold 等人**。
- **recon 终态沿用 L1-L4**（无更细版本）。「样本可能要先处理（解包/解码，如 kungal）」不是新的一层——由**意图的证据标准**（「解码后才算」）+ **agent 自觉去做**（见能力 roadmap #2 解码反射）兜，不进 L1-L4。
- **人版本化**：意图被人在 gate 校准 = 出新版本（重新钉，旧版归档）。

**已定（追加）**：
- **审计员 = 一个只读 agent**（deepseek，不换模型）：拿钉死的语义 checklist 翻真实文件、逐条引原文判、自然停下出判决。没有 Python 判官、没有 tool-use 死锁。完整设计见 `docs/审计员设计.md`。
- **人机交互 = 两个工具一条通道**（`request_human_assist` 去操作回 ack / `ask_human` 用话回答回文字），三入口共用（agent 工具 / intake 编译器直调 gateway / gate 直调 gateway），界面就在每个 run 的 dashboard 页。完整设计见 `docs/人机交互通道设计.md`。
- **intake 澄清判断驱动、不卡轮数**（改掉下面「最多一轮 ≤6 问」旧设定）：闸门是「现在还含不含糊」，人在环里天然限流，没人答 → fail closed。

**还开着**：
- **前置 latent bug 先修**：`generate()` 丢 `reasoning_content`（deepseek 把判决放 reasoning 时被静默丢成空）——这也是当前单次审计的潜伏 bug，先单独修 + 单测再上循环。
- 审计员几个待实测回标的旋钮：判决带阈值 λ(0.4/0.75) + 轮数封顶(6) 要用真实 run 校准；稀疏造假（每 N 条混 1 假）只能概率性抓，要不要加采样预算。

> 已 settled 的旋钮（不用操心）：编译失败且无人 → 硬停大声报错；读内容抽查规模 → ~8×1500 默认。

## 9. 不做什么

- 不做意图的字段化 schema（永远自由散文，§六）。
- 审计**不做 Python 判官、不做「必须调提交工具」的 loop**（那会 deepseek 死锁）；审计员是个**只读 agent**，判决 = 它自然停下后的最后一句话。详见 `docs/审计员设计.md`。
- 人不在 audit 的每一步里（审计自主跑）；只有审计**判不准（UNCERTAIN）**时才上报问人。人接触点 = intake/gate 两结构点 + agent/审计员判断的 B/C。
- intake 澄清是**判断驱动的循环**（消除一个具体模糊就停），不卡固定轮数、也不做开放 chat；详见 `docs/人机交互通道设计.md`。
- 数量永不进意图（只定性，universe 由 recon 发现）。
- 不碰 loop detection / runaway 兜底、跨 session 并发 assist（`CLAUDE.md` §八 维持）。

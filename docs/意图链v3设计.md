# 意图链 v3 — 终版设计(红队修订后)

> 适用分支:`feat/intent-audit-askhuman` · 针对 2026-06-10 vndb run 的真实失败 · 本文档即施工图

---

## 1. 核心不变量

**任何一层都不准自己消化"内核要的东西"和"源站实际有的东西"之间的冲突;和解只有一条路:把冲突摆给人 → 人拍板 → 内核重编重 pin → 下游全部从新内核重新推导。**

为什么这是 vndb 失败的正解:那次 run 不是哪个模块坏了,而是三个判断点(checklist 编译器、审计尺子优先级、gate 提问方式)都**在本地悄悄消化了冲突**——编译器把"拒收孤立引语"条款丢掉、按现有引语写了验收标准;审计员看见了冲突却写下"这不是内核要的完整剧本,但 C3 只要求……"然后 PASS;gate 把两份文档并排摆着却没把冲突变成一个问题。每一层都"合理地"妥协了一点,合起来就是静默替换。不变量把"妥协"这个动作从所有 LLM 手里收走,只留给人。

---

## 2. 链路全图

└─────┬───────┘

┌─────────────┐  探索站点。"目标在这个源上不存在,最近的替代是 X
│ 2. RECON     │  (附证据)"= 一等公民发现,不是失败              【改:C3 重新定义】
└─────┬───────┘  recon 审计 C3:定位到真东西 OR 证据确凿的缺席

│              │  代码路由 CONFLICT → ask → 人:接受折衷(内核 v2

└─────┬───────┘  人拍板:折衷与否
      ▼
┌─────────────┐
│ 5. HARVEST   │  不动。checklist sha-pin、防篡改照旧
└─────┬───────┘
      ▼
┌─────────────┐  ★第三道闸★ 尺子优先级条款(briefing + 审计员

│              │  checklist 只是它的展开。交付物技术上满足某条
│              │  criterion 但命中内核点名拒收的替代品 → 内核赢,

### 每一环明细(标注【红队】= 红队 sustained 修正案改出来的)

**1. INTAKE — 不动。** CLARIFY 口 + 强制人工确认 + pin,实跑验证过。唯一改动在 `_pin()`:写新内核前把旧的改名为 `intent_kernel.prev.md`,新内核头部加一行 `<!-- pinned: 原因 -->` 注释记录这次 pin 是初始还是 gate 折衷。【红队:原案的 v{n} 完整版本链被裁定过度,降为一级存档 + 注释内由来】

**2. RECON — 一处重新定义。** "目标在此源上不存在"成为合法的一等发现。但【红队】给"缺席"加了证据门槛,否则这是新的偷懒口:
- `_RECON_CRITERIA` 的 C3 改写:定位到真东西 **或** 证据确凿地确立缺席(站方文档明说没有 / 完整目录可枚举且目标不在列 / 搜索穷尽且记录了查询与结果数)。**"我搜了没找到"不附证据 = FAIL。**
- 审计员 system prompt 加一条纪律:区分"我没找到 X"和"我找到了 X 不存在的证据",证据薄就 FAIL 该项。
- planner system prompt 加"缺席作为完成信号"一节:认为目标不存在时,用 `mark_done(status='blocked')` 附上可引用的来源。planner 只负责诚实取证,**不预判内核接不接受**——内核裁决权留在审计时。【红队:原修正案让 planner 读内核预判,被驳回】
- checklist 编译器对应加"故意缺席"指引:procedural/内核记录了证据确凿的缺席时,全集覆盖 criterion 不适用,改写为"验收 = 缺席证据本身在场"。

**人在哪拍板:** recon 不打扰人;缺席的最终裁决在审计 + gate。

**3. GATE — 主要的新牙齿。** 现状(`src/cli/gate.py`)只把策略报告 + 内核并排给人看,没有任何 LLM 比对——vndb 正是从这里漏的。v3:
- 新函数 `alignment_judgment()`(放 `src/cli/alignment.py`):读内核证据标准 + 策略报告 + **真实读最多 3 个 samples/ 文件的内容**(各前 ~2000 字),一次新上下文 LLM 调用,输出**一段自由散文评估 + 末行一个口子**——没问题,或一段"给人的问题 + 证据摘录"。【红队:原案的 ALIGNED/SUBSTITUTE/PARTIAL 三分类枚举被打掉——那是变相 typed enum。代码只认二元"要不要问人",和 intake 的 CLARIFY 同构;三选项(接受/转向/停)出现在**给人的问题文本里**,由人的回答 + LLM 解释路由,不由代码 parse 分类】
- 判定结论**永远展示给人**(连"没问题"也展示为一行参考),并附"我不同意判定"的直通——人可以无视判定照常继续或停。【红队:黑箱判定违反"人拍板"原则】
- 人选"接受替代"→ 调 `compile_intent_kernel`,**把判定的具体发现 + 人的批准文本作为 clarification 种子传进去**(加一个可选参数),折衷被明文写进 v2 的证据标准,人再确认一次草稿,重 pin。【红队:原案直接从老需求重编,折衷内容会丢,造成范围漂移】
- 重编失败不再静默继续:明确告诉人"重编没成,用原内核继续还是停",人再选。【红队:现在 gate.py 里 except 后默默 CONTINUE】
- gate 重 pin 之后,在 strategy_report.md 末尾追加一行"内核已在 gate 调整,以上发现按旧标准写成"。【红队:防止后人读 run 目录困惑】
- 无人值守 / no-gate:没问题 → 自动继续(现有决策);有问题 → ask 渠道挂起,**带超时,超时按停处理**,绝不带着已知替换自动继续。
- **实现前先写 `docs/gate_judge_spec.md`**:判定的 system prompt + 一个 worked example(就用 vndb 那次:输入"只有社区短引语"+ "要完整剧本、拒引语合集"的内核,标注期望输出)。【红队:不写规格的"判定会沉默"是不可证伪的承诺】

**人在哪拍板:** 接受替代 / 转向 recon / 停,三选都在 gate 的人手里;v2 草稿还要人二次确认。

**4. CHECKLIST 编译 — 兜底闸。** 现状(`src/harvest/checklist.py`)无逃生口:必须产出清单,LLM 挂了还写 stub 继续(fail-open)——vndb 静默缩水的直接机制。v3:
- `_COMPILE_SYSTEM_PROMPT` 加"可满足性检查"段:写清单前必须核对内核证据标准能否从实际可得数据验证;不能 → 在输出最前面给 `CONFLICT:` 标记 + 一段原因与证据,不写清单。明确告诫:**不许把标准削弱、改述去迁就现有数据**;若照标准写出的 criteria 现有数据注定过不了,也照写,审计去裁。【红队:原 prompt 的"use whatever subset catalog/ presents"被指认为鼓励静默替换的措辞】
- 返回值从 bool 改为字符串(写盘内容原样返回),launcher 用 `startswith("CONFLICT:")` 检测——标记法,不是 typed enum。【红队:tuple/枚举方案被裁定违反设计哲学】
- launcher 路由:CONFLICT → ask 渠道(问题文本里嵌内核摘录 + 证据;放不下就写 `workspace/conflict_decision_context.md` 并在问题里给路径,**不新增 gateway 接口**【红队】)→ 人:接受折衷(内核 v2 + 重编**一次**)/ 停。
- 迭代界【红队】:单次重编语义。重编后若再 CONFLICT,**仍回到人**(不自动 FAIL——保留人的决定权),问题里注明"这是第二次冲突";每轮记 `workspace/checklist_compile_log.json`(内核版本 + 编译输出 + 人的决定),防无限循环变成无人察觉的卡死。
- LLM 挂掉的 stub 路径改 **FAIL-CLOSED**:launcher 检测到编译失败不再带着 stub 静默开采;有人 → ask(重试编译 / 接受弱 stub 继续 / 停),无人值守 → 直接停。【红队:stub 也是张能 parse 的清单,审计员分不出它是兜底货——这正是 vndb 机制】
- 清单里嵌一行 `<!-- compiled from intent kernel sha256:xxxx -->`,供审计期检测内核漂移。【红队】

**人在哪拍板:** 冲突时的折衷与否;stub 弱合同要不要接受。

**5. HARVEST — 不动。** sha-pin、防篡改、watchdog 全保留。

**6. AUDIT — 尺子优先级。** 现状:briefing 里内核叫 "YOUR RULER" 但只是修辞,criteria 才是审计员逐条核的锚——vndb 审计员就是被锚拽着 PASS 的。v3:
- `_build_harvest_briefing` 加先例条款:"当前 pin 的内核是最高尺子,checklist 是它的操作展开。交付物技术上满足某条 criterion 但命中内核点名拒收的替代品时,内核赢:报 UNCERTAIN,不按 checklist 单独给 PASS 或 FAIL。"
- `_AUDITOR_SYSTEM_PROMPT` 加两句:① 证据命中证据标准里**点名拒收的替代品**,该 criterion 即不成立,拒收清单覆盖 criterion 的通过条件;② 发现 checklist 允许而内核拒收的**合同与尺子冲突** → 报 UNCERTAIN 并在 verdict 里写明冲突(checklist 说什么 / 内核说什么 / 盘上是什么),这意味着需要人重谈内核。【红队:原案让冲突走 FAIL——但 FAIL 会把 worker 锁进"修数据"死循环,它没有任何工具能改内核或喊人;改走 UNCERTAIN,现成的 adjudicate 路就把它送到人面前,mark_done 零新解析】
- 内核 mark_done 时从盘上现读(现状已如此)→ 重 pin 的 v2 自动成为尺子,零代码。
- mark_done 时比对清单内嵌的内核 sha 与当前内核 sha,漂移 → 把事实写进 briefing 给审计员掂量(代码只发现布尔事实,意义由审计员判,拿不准走 UNCERTAIN→人)。【红队】
- 审计员加第二个 nudge【红队】:PASS 且只读过 1 个文件却要认证 3+ 条 criteria 时,推一次"再开 2-3 个样本、逐个引证"——是提醒不是机械否决。

**人在哪拍板:** 不拍板;审计员只产出 verdict,冲突一律升级成 UNCERTAIN 交给第 7 环的人。

**7. UNCERTAIN → 人裁 — 基本不动。** 两处小改【红队】:
- 问人的措辞加具体问题类型提示("数据不足/格式不对/无法验真/权限受限……"),让 agent 拿到的反馈可执行,避免"不够"三个字来回打转;docstring 写明:人反复拒、agent 又拿不出新证据时,出口是 `mark_done(status='blocked')`,以及 3 小时 watchdog 是最终兜底。
- 无人值守(HELMSMAN_RUN=1):所有 `timeout_s=None` 的 ask 改为 `Config.HUMAN_ASSIST_TIMEOUT_S`,超时按拒绝/停处理并大声记日志——挂起是对的,但无通知渠道的永久挂起不行。有人值守的 gate 保持永等。

## 3. 三道闸怎么各自挡住 vndb 那次 run

那次的事实:需求要完整游戏剧本;内核 v1 明文写"孤立引语合集必须拒";recon 只找到社区短引语,把不匹配写成策略脚注;gate 两文档并排、人点了继续;编译器按引语写了 criteria、丢了拒收条款、sha-pin;审计员读了真文件、亲眼看见冲突、写下"这些不是内核要的完整剧本,但 C3 只要求……"然后 PASS。

**第一道(gate 对齐判定):** 判定 LLM 拿到的输入是内核那句"孤立引语合集必须拒"+ 真实打开的样本文件(满屏短引语)。这不是策略报告里的脚注,是直接对撞——判定必然产出"有问题要问人",gate 的问题从"确认继续?"变成"内核拒收引语,但站上只有引语,证据摘录如下。接受引语(内核改 v2)/ 让 recon 换路 / 停?"。那次人面对的就不再是两份要自己交叉比对的文档,而是一个被摆明的选择题。

**第二道(编译器 CONFLICT):** 假设 gate 被跳过(--no-gate 或 harvest --from-run)。编译器读到内核"拒孤立引语"+ catalog/samples 全是引语,可满足性检查命中 → 输出 `CONFLICT: 内核要求完整对白剧本并点名拒收引语合集;catalog 仅含社区短引语(样本 xx.json 内容为单句引语)`,**没有清单产出**。launcher 检到标记 → 问人。那次真实发生的"把拒收条款丢掉、按引语写 criteria、sha-pin 成合同"在机制上不可能了:要么照内核写标准(引语数据过不了第三道闸),要么 CONFLICT 停下问人。stub 兜底路也封死——LLM 编译失败不再静默开采。

**第三道(审计先例条款):** 假设前两道全失灵,引语味的 checklist 还是 pin 上了。审计员读文件后写下的那句"这些不是内核要的完整剧本,但 C3 只要求文件非空且反映需求"——正是先例条款逐字针对的句式。新规则下,这个观察本身就是触发条件:满足 criterion + 命中内核拒收清单 = 内核赢 = UNCERTAIN + 冲突说明。同一个审计员、同一批文件,verdict 从 PASS 变成 UNCERTAIN,走 adjudicate 到人面前:"checklist 说引语可以,内核说拒,盘上是引语——你裁。"

三道闸相互独立:gate 闸靠新上下文判定,编译闸靠可满足性自检,审计闸靠先例条款,任何一道单独工作都足以把那次 run 从静默 PASS 变成"人面前的一个问题"。

## 4. 红队改掉的设计点(诚实清单)

1. **三分类枚举被打掉。** 原案 gate 判定输出 ALIGNED/SUBSTITUTE/PARTIAL 三个固定类、代码分三路——被裁定为变相 typed enum,违反§六。改为:自由散文评估 + 单一二元口子(要不要问人),三个选项活在给人的问题文本里,由人的回答路由。
2. **"三道闸任意一道都能挡 vndb"原案是虚的。** 红队逐文件核实:对齐判定在代码里不存在、连 prompt 规格都没有;CONFLICT 槽不存在,且 stub fail-open 直接绕过它;先例条款在 briefing 里也不存在("YOUR RULER"只是修辞)。本文档补齐了全部三处的落点与规格——原案是承诺,现在才是设计。
3. **审计冲突从 FAIL 改为 UNCERTAIN。** 原案"内核赢 → FAIL or UNCERTAIN"——红队指出 FAIL 会把 worker 锁进徒劳的修数据循环(它改不了内核、喊不了人),UNCERTAIN 才接得上现成的人裁通路。
4. **"Clean runs 零新打扰"措辞修正。** 零新人工打扰成立(对齐时不加问题),但每个 harvest 任务多 1 次 LLM 调用、gate 前多 10-30 秒,且判定结论展示给人(不是 silent)。成本如实写明。
5. **CONFLICT 无迭代界 → 单次重编 + 二次冲突仍回人 + 编译日志。** 原案没说重编后再冲突怎么办——可能变成消耗人力的死循环。
6. **kernel v{n} 完整版本链 → 一级 .prev 存档 + 注释内由来。** 完整版本系统被裁为 bloat。
7. **recon "缺席"重定义被加上证据门槛。** 原案的"establishing absence with evidence"没定义什么算证据,开了新的偷懒口;现在 C3 文本里写死三类有效证据 + "无证据缺席 = FAIL"。
8. **无人值守永久挂起 → 超时 fail-closed。** 原案说"SUBSTITUTE → ask-channel hold"但没说挂多久;红队证实无通知渠道时这是看不见症状的死等。
9. **编译器返回 bool → 字符串标记。** CONFLICT 装不进 bool;红队同时驳回了 tuple+枚举方案,定为 marker 法(同 intake 的 ---CLARIFY---)。
10. **gate 重编失败静默继续 → 明示人。** 现状 except 后默默用原内核 CONTINUE,人不知情。

---

## 5. 考虑过,不改,因为

- **harvest 进行中内核被重 pin 导致审计错位** — 不改:该代码路径不存在。gate 永远在 harvest 启动前同步完成,审计在 mark_done 时从盘上现读内核;不为假想的未来功能加版本元数据。
- **并发 hold 耗尽槽位 / 无人值守一律禁问** — 不改:WebGateway 每个请求是独立 uuid 信号文件,没有共享槽池;run 挂起等人是**正确行为**不是故障,该让操作员看见并处理(超时兜底已加)。
- **gate 里再补一次"重编 checklist"** — 不改:launcher 启动时本来就从盘上现读当前内核再编清单,gated 路径天然用上 v2,在 gate 里编是重复机制。

## 7. 残留风险(诚实)

1. **三道闸是同一个模型在判。** judge、编译器、审计员全是 deepseek-v4-pro;fresh context 挡得住"被叙事带偏",挡不住模型本身的同向偏差(都倾向"差不多就行")。三道同时漏的概率被乘法压低了,不是零。
2. **对齐判定自己会错。** 误报(对齐说成不对齐)多打扰人一次,有"不同意判定"直通兜着;漏报(不对齐说成对齐)还有后两道闸——但见第 1 条。
3. **"缺席证据"的穷尽性没有机械下限。** 标准写了要 definitive evidence,但"搜索够不够穷尽"终究是审计员的语义判断,表面化搜索 + 像样的引用仍可能蒙混。
4. **人是最后一环,也是不设防的一环。** gate 把冲突摆上来了,人不读照点"接受",系统按设计服从——v2 由人确认即为合法。这是"human decides"的代价,不是 bug。
5. **无人值守超时 fail-closed 有误杀。** 真只需要人五分钟的 run,人不在就停了。取舍是宁停不错采,操作员可调长 `HUMAN_ASSIST_TIMEOUT_S`。
6. **操作员手改盘上文件不设防。** 同时改 kernel + 重算 sidecar 能骗过全部 sha 体系——信任边界本来就不含防操作员(§七:操作员完全可信)。
7. **内核-清单 sha 漂移只是"摆给审计员看"。** 不是硬停;审计员可以判定漂移无关紧要。这是有意的(LLM 判断、代码路由),但意味着漂移 + 审计员走神的组合仍可能漏。
8. **UNCERTAIN 来回打转仍可能耗尽 3 小时 watchdog。** 措辞改良 + blocked 出口降低了概率,没有消除;最终兜底还是墙钟。
